# Авторизация, JWT и роли — шаги 7–9

## Методы

Все тела запросов — JSON. Ответы с данными авторизации содержат Cache-Control: no-store.

| Метод | Путь | Запрос | Результат |
|---|---|---|---|
| POST | `/api/auth/register` | username, email, password | 201, UserResponse; всегда USER |
| POST | `/api/auth/login` | username, password | 200, пара токенов и пользователь |
| POST | `/api/auth/refresh` | refreshToken | 200, новая пара; прежний refresh отзывается |
| POST | `/api/auth/logout` | refreshToken | 204; refresh отзывается |
| GET | `/api/auth/me` | Authorization: Bearer accessToken | 200, текущий пользователь |

register/login/refresh/logout не требуют access-токена: refresh и logout
проверяют переданный refresh-токен самостоятельно. Клиент не добавляет Bearer
к этим четырём методам, чтобы истёкший access не мешал обновлению сессии.

UserResponse содержит id, username, email и role; в нём нет пароля/хеша.
Пара токенов имеет вид:

```json
{
  "accessToken": "<signed-access-jwt>",
  "refreshToken": "<signed-refresh-jwt>",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "refreshExpiresIn": 604800,
  "user": {"id": 1, "username": "reader", "email": "reader@example.org", "role": "USER"}
}
```

Регистрация проверяет формат данных и уникальность имени/email без учёта
регистра. Дополнительное поле role не назначает права. Пароль кодируется BCrypt
с индивидуальной солью; открытый пароль не хранится. Неверные имя/пароль при
входе дают одинаковую ошибку 401. Некорректные регистрационные данные дают 422,
конфликт уникальности — 409.

## Токены

Подпись HS256 создаёт NimbusJwtEncoder из Spring Security. JWT_SECRET — Base64
от минимум 32 случайных байтов; рабочего значения по умолчанию нет. Access и
refresh имеют разные audience и token_use. Decoder проверяет подпись, фиксированный
алгоритм HS256, issuer, audience, назначение, срок действия и обязательные claims.
Refresh не принимается вместо access, access не принимается на refresh-методе.

По умолчанию access действует 15 минут, refresh — 7 дней. JWT_ACCESS_TTL и
JWT_REFRESH_TTL меняют сроки. При успешном обновлении выдаётся новая пара,
прежний refresh получает revoked_at. Проверка и замена выполняются в одной
транзакции с блокировкой строки: параллельное повторное использование даёт
один успешный ответ, остальные — 401.

В refresh_tokens сохраняются UUID/jti, пользователь, SHA-256-хеш подписанного
refresh JWT и временные поля. Открытых refresh-токенов в БД нет. При обновлении
проверяются сохранённый хеш, владелец, срок и отсутствие отзыва. Повторное
использование старого refresh, истечение и неизвестный токен дают 401.

Выход отзывает переданный refresh и удаляет локальную сессию. Уже выданный access
остаётся действительным до своего истечения; другие сеансы пользователя не
отзываются. Удаление пользователя немедленно лишает его доступа, поскольку
пользователь и актуальная роль проверяются по БД при каждом access-запросе.

## Права

USER и ADMIN получают список/досье, поиск, фильтры, сортировку, страницы и QUERY.
Только ADMIN выполняет POST/PUT/PATCH/DELETE студентов. Анонимный запрос к данным
даёт 401; недостаточная роль — 403. Роль из сохранённой БД является источником
прав, даже если claim role в ранее подписанном JWT устарел.

Правила действуют в SecurityFilterChain и через @PreAuthorize на JpaStudentService.
Подмена роли в sessionStorage или отображение скрытой кнопки не даёт прав на сервере.
Все ошибки, включая JWT, CORS и доступ, используют ApiError с полем error.

## Первый ADMIN

По умолчанию bootstrap выключен. Для создания первого администратора при
первоначальной настройке можно задать BOOTSTRAP_ADMIN_ENABLED=true и
BOOTSTRAP_ADMIN_USERNAME, BOOTSTRAP_ADMIN_EMAIL, BOOTSTRAP_ADMIN_PASSWORD.
Параметры проверяются теми же правилами, что регистрация; в БД попадает BCrypt-хеш.

Повторный запуск не меняет пароль существующего ADMIN с совпадающим именем/email.
Совпадение с USER или другим email останавливает bootstrap с ошибкой: аккаунт
не повышается до ADMIN. Публичного метода повышения роли нет. После создания
ADMIN bootstrap следует выключить. Launcher уже создал рабочий ADMIN admin,
выключил bootstrap и очистил его пароль в .env. Данные входа сохранены локально
в ../../.runtime/admin-credentials.json и исключены из Git. Первоначальная
настройка описана в ../../RUN.md; повторные старты сохраняют пароль.

## Статический клиент

config.js задаёт адрес API; auth.js добавляет Bearer, обрабатывает 401 и управляет
сессией. При истёкшем access выполняется один общий refresh для параллельных
запросов вкладки, затем исходные запросы повторяются не более одного раза.
403 не вызывает refresh или выход. При отказе refresh с 401 сессия очищается;
при временной сетевой ошибке сохраняется для повторной попытки.

Оба токена и безопасное представление пользователя находятся в sessionStorage.
Пароль не записывается; токены не передаются через URL. При загрузке каждой
защищённой страницы /me обновляет роль; для USER скрыты кнопки изменений и
закрыта страница формы. login.html совмещает вход и регистрацию; после регистрации
клиент выполняет обычный вход. Переход next допускает только страницы приложения.

CORS разрешает http://127.0.0.1:5500 и http://localhost:5500, в том числе QUERY и
Authorization. Другие адреса задаются CORS_ALLOWED_ORIGINS. Cookie-авторизация
не используется, credentials отключены. CORS стоит перед проверкой JWT, поэтому
ответы 401/403 доступны разрешённому клиенту. OPTIONS не расходует rate limit.

Лимит применяется к запросам /api/* после допуска Security. Ошибки JWT и
недостаточные права до счётчика не доходят. Регистрация, вход и refresh доступны
до аутентификации, поэтому их попытки, включая неправильный пароль или refresh,
учитываются: отказ там возникает уже в контроллере/сервисе.
