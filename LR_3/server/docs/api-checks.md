# Шаг 10: Swagger/OpenAPI и коллекция Postman

Документация и коллекция готовы. Рабочее окружение настроено; start.cmd запускает
приложение. На этом компьютере SERVER_PORT=8081: в адресах ниже нужно использовать
8081 вместо примера 8080. Инструкция запуска и данные ADMIN — в ../../RUN.md.

## Swagger

- UI: `http://127.0.0.1:8080/swagger-ui.html`.
- OpenAPI JSON: `http://127.0.0.1:8080/v3/api-docs`.
- OpenAPI YAML: `http://127.0.0.1:8080/v3/api-docs.yaml`.
- Исходный контракт: `src/main/resources/openapi/students-api.yaml`.

При другом SERVER_PORT меняется порт в адресах. Документация открывается без
авторизации, а доступ к данным студентов по-прежнему требует JWT и нужную роль.

В Swagger можно раскрыть метод, нажать **Try it out**, заполнить параметры или
JSON и выполнить запрос. Чтобы обращаться к защищённым методам:

1. Выполнить `/api/auth/login` с существующим аккаунтом.
2. Скопировать `accessToken` из ответа.
3. Нажать **Authorize**, вставить только токен, без слова `Bearer`, подтвердить.
4. Выполнить GET списка/досье; для изменения нужен аккаунт ADMIN.

Для register/login/refresh/logout Bearer не требуется. Refresh передаётся в
JSON-теле; после успешного обновления нужно сохранить оба новых токена и
обновить access в Authorize. Swagger не хранит авторизацию после перезагрузки.

Описаны схемы всех тел и ответов, обязательные поля, диапазоны, валидация,
различия PUT/PATCH, связанные поля заселения, параметры поиска/фильтров/страниц,
сортировка, роли, ошибки и Retry-After. Пароли/хеши сущностей не включены в ответы.

### QUERY

OpenAPI 3.0 не содержит стандартного поля операции `query`. Нестандартный
`QUERY /api/requests` описан расширением `x-query` в JSON/YAML и в тексте GET.
Swagger UI не рисует для него отдельную кнопку выполнения. Запрос №09 коллекции
использует настоящий HTTP-метод QUERY и передаёт критерии JSON-телом.
Нового POST-адреса для имитации QUERY не добавлено.

Контракт загружается Springdoc из YAML через OpenApiConfiguration. Автоматическое
сканирование двух контроллеров скрыто @Hidden: иначе raw JsonNode и специальное
условие QUERY дали бы неточные схемы и лишние операции. При изменении API нужно
обновлять YAML; ApiDocumentationIT проверяет опубликованные маршруты/методы,
схемы, настройки безопасности и доступ к UI.

## Коллекция Postman

- `postman/LR3.postman_collection.json` — коллекция формата v2.1.
- `postman/local.postman_environment.example.json` — пример окружения с пустыми
  паролями и токенами.

В Postman импортируются оба JSON-файла и выбирается импортированное окружение.
Для выполнения нужны только три исходных значения:

| Переменная | Значение |
|---|---|
| baseUrl | Адрес Java без `/api`, например `http://127.0.0.1:8080` |
| adminUsername | Имя существующего ADMIN |
| adminPassword | Его пароль |

ADMIN создан при первоначальной настройке: имя admin, пароль в
../../.runtime/admin-credentials.json. Для текущего запуска baseUrl —
http://127.0.0.1:8081. Остальные переменные генерируются автоматически.
Поля паролей и токенов в примере отмечены как secret. Для передачи другому
человеку используется исходный пример с пустыми значениями.

Запускать следует всю коллекцию по порядку **01 → 30**, через Collection Runner
либо последовательно вручную. Зависимости между запросами намеренные:

| Запросы | Что демонстрируют |
|---|---|
| 01–05 | Состояние сервера, вход ADMIN, регистрация и вход USER, текущая роль |
| 06–09 | Создание ADMIN, чтение USER, поиск/фильтры/сортировка/пагинация, QUERY |
| 10–13 | USER получает 403 при попытках POST/PUT/PATCH/DELETE |
| 14–19 | PATCH, отказ некорректного PATCH, сохранность данных, PUT со сменой ИСУ, 404 старого ИСУ и 409 дубликата |
| 20–24 | Обновление пары USER, отказ старого refresh, отказ access вместо refresh, новый access, 401 анонимного запроса |
| 25–30 | Удаление студента, проверка 404, выход USER/ADMIN, отказ refresh после выхода, очистка переменных токенов |

403, 404, 409 и 422 в соответствующих запросах — ожидаемые результаты: проверки
должны проходить. Tests/Post-response scripts проверяют статусы, тела и единый
формат ошибок. Пара токенов автоматически сохраняется отдельно для ADMIN и USER;
после ротации используется новый refresh. Всего 30 запросов и 61 проверка.

Коллекция создаёт нового пользователя `lab3_demo_*` и одну запись студента.
Случайный ИСУ не перезаписывает существующую запись: создание должно дать 201,
иначе выполнение останавливается. Изменение и удаление используют только ИСУ,
сохранённый после успешного создания. В конце студент удаляется; аккаунт USER
остаётся, поскольку публичного удаления пользователей нет. При прерванном запуске
`createdStudentIsu` указывает на созданного коллекцией студента. Поэтому для
демонстрации и автоматического прогона предназначена отдельная тестовая БД.

## Newman — необязательный запуск из терминала

Newman добавлен только как devDependency; frontend не требует его для работы.
После подготовки окружения можно скопировать пример в
`server/docs/postman/local.postman_environment.json`, заполнить три исходных
поля и из LR_3 выполнить:

```powershell
npm ci
npm run test:api
```

Этот локальный JSON с реквизитами исключён из Git. Скрипт запускает только
проверки уже работающего API: он не запускает Java, PostgreSQL или frontend.
При первой ошибке Newman останавливается (`--bail`).
