# Контракт API студентов

Документ описывает реализованный на шагах 1–10 контракт переноса из Django в Spring
Boot. HTTP-операции студентов, транзакционный сервис, валидация и обработка ошибок
готовы. Регистрация, вход, JWT и роли реализованы; анонимный доступ к данным закрыт.
Контракт авторизации находится в [authentication.md](authentication.md).

## Адреса и права

Сохраняем `/api/requests`, без обязательного завершающего `/`.
Новый сервер по умолчанию слушает `http://localhost:8080`.
Все студенческие операции требуют access JWT
в `Authorization: Bearer <accessToken>`.

| Метод | Путь | Результат | Роли |
|---|---|---|---|
| GET | `/api/requests` | Список, 200 | USER, ADMIN |
| QUERY | `/api/requests` | Список с параметрами в JSON, 200 | USER, ADMIN |
| GET | `/api/requests/{isu}` | Один студент, 200 | USER, ADMIN |
| POST | `/api/requests` | Созданный студент, 201 | ADMIN |
| PUT | `/api/requests/{isu}` | Полностью обновлённый студент, 200 | ADMIN |
| PATCH | `/api/requests/{isu}` | Частично обновлённый студент, 200 | ADMIN |
| DELETE | `/api/requests/{isu}` | 204, без тела | ADMIN |

PUT — добавление по ТЗ ЛР 3. Остальные методы уже есть в исходном API.
QUERY сохраняется: его вызывает `main.js`. Для него добавлены HTTP-маршрутизация
и разрешение в Spring Security firewall и CORS для Live Server.
Обычного GET достаточно
для тех же критериев; QUERY предоставляет совместимый вариант с телом.
OpenAPI 3.0 не имеет стандартного поля операции `query`; этот метод описан
расширением x-query и запросом №09 коллекции Postman (см. api-checks.md).

## Представление студента

```json
{
  "isu": 123456,
  "fio": "Иванов Иван Иванович",
  "group": "M3301",
  "dorm": 1,
  "room": 101,
  "date": "2026-09-01",
  "isForeigner": false,
  "notes": "Заметка"
}
```

| Поле | Тип | Правило, переносимое из текущего проекта |
|---|---|---|
| isu | integer | Обязательно, шесть цифр, уникально |
| fio | string | Обязательно, три слова на русском с заглавных букв, максимум 150 символов |
| group | string | Обязательно, заглавная латинская буква и четыре цифры; максимум 10 символов |
| dorm | integer или null | 1–999 |
| room | integer или null | 1–9999 |
| date | string или null | Дата заселения, `YYYY-MM-DD`, год от 2000 |
| isForeigner | boolean | По умолчанию false |
| notes | string | По умолчанию пустая строка, максимум 500 символов |

Для заметок считаются Unicode-символы, как в PostgreSQL VARCHAR(500), а не
кодовые единицы UTF-16; emoji также считаются одним символом кода Unicode.

Общежитие, комната и дата либо заполнены вместе, либо все равны null.
Внутренний `id` таблицы не входит в JSON. URL по-прежнему использует ИСУ.
Нормализация строк, пустых значений необязательных полей и допустимых числовых
строк реализована в StudentInputParser и StudentValidator перед изменением сущности.
Дробные числа, объекты и логические значения в числовых полях отвергаются.
isForeigner принимает JSON boolean или строки true/false без учёта регистра;
строка false корректно означает false. null у notes нормализуется в пустую строку.

POST требует `isu`, `fio`, `group`; отсутствующие необязательные поля получают
значения по умолчанию. PUT полностью заменяет представление существующей записи:
те же три поля обязательны, пропущенные необязательные поля сбрасываются к
значениям по умолчанию. Отсутствующий студент при PUT даёт 404, а не создание.

PATCH меняет только переданные поля. Пропуск поля отличается от явного null.
Например, `{"notes":"Новая заметка"}` сохраняет текущее заселение, а
`{"dorm":null,"room":null,"date":null}` очищает его. После объединения
проверяется полное итоговое состояние студента. Можно менять ИСУ: занятый ИСУ
даёт 409, успешный ответ содержит новый ИСУ; внутренний id не меняется.
Неизвестные поля студента игнорируются, как в исходном сериализаторе.

## Список: поиск, фильтры и страницы

```text
GET /api/requests?page=1&limit=20&search=Иванов&group=M3301&sort=fio,asc
```

| Параметр | Значение |
|---|---|
| page | Номер страницы от 1; по умолчанию 1 |
| limit | Размер страницы 1–100; по умолчанию 20 |
| search | Подстрока в ФИО или заметках, без учёта регистра; пробелы по краям удаляются |
| group | Точное совпадение группы |
| dorm | Номер общежития |
| room | Номер комнаты |
| isForeigner | true / false |
| sort | Новый параметр: `поле,asc` или `поле,desc` |

Совместимость пагинации: page < 1 заменяется на 1, limit вне 1–100 — на 20;
если page или limit невозможно разобрать как целое, оба получают значения по
умолчанию. Неизвестные параметры фильтрации игнорируются. Ошибки известных
фильтров возвращают 400. Фильтры комбинируются через AND; поиск по ФИО и
заметкам — через OR внутри этого условия. Сначала применяются критерии и
сортировка, затем выбирается страница; total считается по всем совпадениям.

Разрешённые поля сортировки: `isu`, `fio`, `group`, `dorm`, `room`, `date`,
`isForeigner`, `notes`. Поля SQL из запроса не подставляются: нужен белый список.
Без sort используется порядок создания (внутренний id ASC). Для выбранной
сортировки id ASC добавляется как критерий при равенстве, чтобы страницы были
стабильны. Неизвестное поле или направление сортировки даёт 400.

QUERY получает плоский объект с теми же параметрами:

```json
{
  "page": 1,
  "limit": 20,
  "search": "Иванов",
  "group": "M3301",
  "isForeigner": false,
  "sort": "fio,asc"
}
```

Тело QUERY должно быть JSON-объектом; search — строкой либо null (пустой поиск).
GET и QUERY возвращают одинаковую структуру:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 0,
    "total_pages": 0,
    "has_next": false,
    "has_prev": false
  }
}
```

Имена `data`, `total_pages`, `has_next`, `has_prev` сохраняются ради клиента.
Пустая выборка имеет total_pages = 0; выход за последнюю страницу даёт пустой
data, а не 404. has_next = page < total_pages; has_prev = page > 1.

## Ошибки

```json
{
  "error": "Ошибка валидации",
  "details": {"isu": "Студент с таким ИСУ ID уже существует"}
}
```

`error` — строка; `details` — необязательный объект. В нём допускаются строковые
сообщения по полям и числовые служебные значения, например retry_after.
Стектрейсы, SQL, пароли и токены в ответы не включаются.

| Статус | Ситуация |
|---|---|
| 400 | Некорректный JSON, отсутствующие обязательные поля POST/PUT, ошибочные фильтры/сортировка |
| 401 | Отсутствующий, недействительный или истёкший access-токен |
| 403 | Авторизация есть, но прав недостаточно |
| 404 | Студент не найден |
| 409 | Конфликт уникальности ИСУ, имени пользователя или email |
| 422 | Нарушение правил полей/совместного заполнения, в том числе итогового состояния PATCH |
| 429 | Превышение лимита запросов, с заголовком Retry-After |
| 500 | Непредвиденная ошибка, подробности только в серверном логе |

Существующий лимит 100 запросов за 60 секунд на IP перенесён в RateLimitFilter.
Фильтр выполняется после Security: учитываются допущенные к API запросы,
OPTIONS не учитывается. Превышение даёт JSON 429 с Retry-After и details.retry_after.
Счётчик рассчитан на один процесс приложения; предел задаёт RATE_LIMIT_MAX_REQUESTS.
Поддержка CORS для браузерных preflight OPTIONS настроена. Публичные методы
register/login/refresh/logout учитываются счётчиком, включая неудачные попытки.
Доверие X-Forwarded-For по умолчанию
выключено, как в текущем проекте.

## Граница текущего этапа

Без access JWT доступны GET `/actuator/health`, OPTIONS API и POST-методы
register/login/refresh/logout. Доступ к данным требует валидного access JWT и
соответствующей роли. Health включает
проверку соединения с PostgreSQL, но не публикует детали подключения.
api.js и QUERY уже подключены к Java через Auth.fetch. Swagger UI, OpenAPI JSON/YAML
и коллекция Postman опубликованы; адреса и порядок демонстрации — в api-checks.md.

## Регистрация

RegistrationRequest и Bean Validation используются эндпоинтом регистрации:
имя длиной 3–64 символа из латинских букв, цифр, _, . и - (первый символ — буква,
цифра или _), корректный email до 254 символов, пароль минимум 8 символов и
максимум 72 байта UTF-8 с учётом BCrypt. Пробелы по краям имени/email удаляются,
пароль не обрезается. Поля role во входном DTO нет. Проверка уникальности
имени/email обеспечена индексами БД и проверкой сервиса. Назначение USER,
BCrypt-хеширование, выпуск и ротация JWT реализованы; подробности в authentication.md.
