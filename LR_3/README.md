# Лабораторная 3

Вариант: **Spring Boot + EclipseLink/JPA + PostgreSQL 17+**.

**Обычный запуск: `start.cmd`. Остановка: `stop.cmd`. Состояние: `status.cmd`.**
Настройка этого компьютера выполнена, импортированы 122 студента и создан ADMIN.
Адреса, данные входа и объяснение запуска — в [RUN.md](RUN.md).

Реализованы шаги 1–10: сервер студентов, валидация, регистрация/вход, JWT
access/refresh, роли ADMIN/USER, статический интерфейс, Swagger/OpenAPI и Postman.

- `server/` — Java-проект; [инструкция сервера](server/README.md).
- `login.html` — вход и регистрация.
- `index.html`, `form.html`, `dossier.html` — список, форма и досье студентов.
- `config.js` — адрес Java API; по умолчанию `http://127.0.0.1:8080/api`.
- `auth.js` — сессия, обновление access-токена и выход.
- [Контракт студентов](server/docs/api-contract.md).
- [Авторизация и роли](server/docs/authentication.md).
- [Проверки](server/docs/verification.md).
- [Swagger и коллекция Postman](server/docs/api-checks.md).

start.cmd запускает локальный сервер страниц вместо отдельного Live Server.
Сейчас сайт доступен на http://127.0.0.1:5500, Java API — на 8081. Сервер страниц
передаёт актуальный адрес API через config.js. Для отдельного ручного запуска
через Live Server используются config.js и CORS_ALLOWED_ORIGINS; параметры
этого режима нужно согласовать с выбранным портом Java.
Запуск через file:// не используется. Сборка frontend не требуется; Node/npm
нужны только для браузерных тестов и необязательного прогона Postman через Newman.

Созданный через форму аккаунт получает USER: список, поиск, фильтры, сортировка
и досье. ADMIN также создаёт, изменяет и удаляет студентов. Кнопки изменения
скрываются для USER, а backend самостоятельно проверяет права на каждом запросе.

Сессия хранится в sessionStorage вкладки. Пароль туда не записывается.
При истечении access-токена клиент один раз обновляет пару токенов и повторяет
запрос; при недействительном refresh возвращает на страницу входа.

Старая Python-реализация сохранена в `api/`, `backend/`, manage.py и requirements.txt.
Она не участвует в новом клиентском потоке. students.json не изменён; его данные
перенесены в PostgreSQL один раз при первоначальной настройке.

Документация после запуска сервера доступна на `/swagger-ui.html`, JSON — на
`/v3/api-docs`, YAML — на `/v3/api-docs.yaml`. Коллекция из 30 запросов и пример
окружения находятся в `server/docs/postman/`; подробности в api-checks.md.

Первоначальная настройка, создание постоянного ADMIN, импорт и единый запуск
выполнены. Скрипты и сохранение данных проверены остановкой/повторным запуском.

## Браузерные проверки

`npm ci`, затем `npm run test:e2e`. Используется установленный Google Chrome в
headless-режиме и отдельный тестовый backend/PostgreSQL. Playwright поднимает
только временный статический HTTP-сервер на порту 5500.

Тестовый Java-сервер должен слушать 18083, использовать отдельную тестовую БД,
JWT_ACCESS_TTL=3s, JWT_REFRESH_TTL=10m, RATE_LIMIT_MAX_REQUESTS=10000 и тестового
ADMIN `e2e-admin` с паролем `e2e-admin-password`. Такой ADMIN можно создать
bootstrap-параметрами только в тестовой БД. Нужен отдельный случайный JWT_SECRET.
E2E_API_URL, E2E_ADMIN_USER и E2E_ADMIN_PASSWORD позволяют менять тестовые адрес
и учётные данные. Тесты создают аккаунты с префиксом e2e_reader_ и используют
ИСУ 887755/887756; не запускай их на рабочей БД.

Playwright подменяет только config.js на тестовый адрес, затем выполняет настоящие
запросы браузер → Spring → PostgreSQL, включая CORS. Он проверяет регистрацию,
USER/ADMIN, весь CRUD в интерфейсе, QUERY, автоматическое обновление токенов при
истечении, параллельные запросы, выход, отзыв refresh и временный сетевой сбой.
Отдельный swagger.spec.cjs открывает Swagger на Java-сервере и проверяет
Authorize/выполнение защищённого GET. Его можно запустить отдельно:
`npm run test:e2e -- tests/browser/swagger.spec.cjs`; короткий access TTL для
этого конкретного теста не требуется.
